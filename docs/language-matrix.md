# Language switching: what actually happens

Generated by `backend-ws/tests/language_matrix.py`, 9 September 2026.

Every ordered pair of the eleven languages Wayfinder claims to support: a
few seconds of synthesised speech in the first language, a beat, then a few
in the second, streamed through a real caption server at the speed a
microphone would deliver it. "yes" means the caption language followed the
speaker.

**68 of 110 pairs followed.** Before this run the claim rested on three
pairs verified by hand in Sprint 1 — all three of which this run
reproduces, which is why its answers are worth reading.

## Arabic does not work, and it is not the switching

**0 of the 20 pairs** involving Arabic followed the speaker. Excluding
Arabic entirely, **68 of 90 did** — so one language out of eleven accounts
for almost half of every failure in the grid.

The switching machinery is fine. `ar-EG → ko-KR` heard
`['hi-IN', 'ko-KR']`: it noticed the change and named Korean correctly.
What it could not do was name Arabic. Every Arabic sample, in either
position, came back as Hindi.

Three checks, because "the test audio is bad" is the first thing to rule
out and the easiest to skip:

- **Pinned to `ar-EG`, the same audio transcribes as Arabic** — 71
  Arabic-script characters, zero Devanagari. The audio is genuinely
  Arabic, and the recogniser handles it correctly when told what it is.
- **More audio does not help.** `chirp_2` returns `hi-IN` at three
  seconds, at five, and at eight. `DETECT_SECONDS` is not the lever, which
  matters because Sprint 1 raised it from two to three for this exact
  symptom — that fix worked on one sample and does not generalise.
- **It is not the speaker.** Six Arabic voices, male and female, all
  detected as Hindi.

So this is a limitation of the detection model, not of this code.

**The workaround already exists.** Since Sprint 5 a signed-in user can pin
a language in settings, which skips detection entirely — and pinned Arabic
transcribes correctly. An Arabic speaker should pin Arabic, and the README
now says so instead of claiming detection covers eleven languages.

## The other failures are the ones the code predicted

Of the 22 remaining failures, most are a language *staying put* rather
than switching to something wrong, and they cluster on Latin-script
European languages as targets: French fails 7 times out of 10, Spanish 6,
German 5, English 5.

`app/stt/auto.py` says why, in a comment written in Sprint 2 before any of
this was measured:

> Related languages fool both cues above.

All three switch triggers need the stream to visibly degrade — confidence
collapsing, results stalling, or nothing finalising. An English-pinned
stream fed French produces confident-looking finals that keep arriving, so
nothing fires and no re-detection happens. The comment was right; nothing
had ever checked what it cost.

`RECHECK_INTERVAL_SECONDS` does not help here. It is a rate limit on
checks that a trigger has already asked for, not a check of its own.

## What would be worth trying next

A fourth trigger: re-detect every N seconds regardless of how healthy the
stream looks. That would plausibly catch the stayed-put cases, at the cost
of a detection call every N seconds of every session — real money, and a
little latency, on every caption session rather than only on broken ones.

Whether that trade is worth making is now a measurable question rather
than a guess, which is the main thing this run changed. Re-running the
matrix takes about forty minutes and answers it.
